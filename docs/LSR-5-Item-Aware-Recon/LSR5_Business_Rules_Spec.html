Section 1

Executive Summary

Core Hypothesis
This is not a simple invoice matching engine. It is a hybrid debtor exposure and cylinder custody reconciliation workbench. The engine reconstructs the true state of a customer's AR ledger from three incomplete sources, then surfaces what remains unresolved with enough context for a human to make a defensible accounting decision.
  • The platform is internal-only, human-in-the-loop, and ERP read-only.
  • Sessions reconcile exactly one debtor account at a time.
  • MVP supports assisted recommendations only — no autonomous allocations.
  • Finance users need commercial AR visibility and CYL custody visibility in the same workspace.
  • ERP running balance is a health signal, not a completion gate — exports may be incomplete by design.
Section 2

Scope & Non-Goals

In Scope — MVP

  • Invoice, payment, and financial credit note allocation assistance.
  • Opening balance handling (positive = invoice-like; negative = credit pool).
  • Journal and Bank UD classification before allocation.
  • Cylinder quantity awareness at sub-ledger level.
  • Persistent customer credit pool tracking across sessions.
  • Operator notes and session completion workflow.
  • Customer flags: allows_cross_bucket_settlement, pays_for_cyl.
  • Rounding write-off up to R1.00 with operator one-click approval.

Out of Scope — MVP

  • ERP writeback of any kind.
  • Autonomous reconciliation without operator confirmation.
  • Machine learning model adaptation.
  • Full yard / SOH cylinder reconciliation (CYL Custody Engine — deferred).
  • Cross-account batch reconciliation.
  • Cross-period allocation rules.
  • Multi-operator concurrent sessions.

Section 4

Core Domain Model

  • Two coupled ledgers exist: Commercial Ledger (value) and Custody Ledger (qty).
  • Commercial settlement and custody settlement are related but distinct.
  • An invoice carries two independent settlement states: financial_state (monetary sub-ledger) and custody_state (cylinder qty). Each resolves independently. financial_state = SETTLED does not require custody_state = RETURNED.
  • Customers may settle CYL commercially (cash) instead of physically returning cylinders.
  • No single data source is complete — the engine triangulates across four sources (ERP summary, detail lines, transaction_headers, transaction_items).
  • The engine recommends; the operator decides. No autonomous allocation in MVP.

Invoice Sub-Ledger Model

An invoice is not a single open balance. It carries four independently tracked components. Settlement requires all components to reach zero.

Schema

invoice_sub_ledger {
  invoice_id             TEXT      -- doc_no from ERP summary
  total_amount           NUMERIC   -- HDR_TOTAL
  lpg_value_balance      NUMERIC   -- sum of LPG line totals
  cyl_value_balance      NUMERIC   -- sum of CYL line totals
  other_value_balance    NUMERIC   -- AGR + unmapped items
  cyl_qty_balance        JSONB     -- { "9.1": 5, "14.1": 2 } per SKU
  financial_state        TEXT      -- OUTSTANDING | SETTLED | EXCEPTIONED | WRITTEN_OFF | IGNORED
  custody_state          TEXT      -- OUTSTANDING | PARTIALLY_RETURNED | RETURNED | COMMERCIALIZED | DISPUTED | IGNORED
Note — State Independence
financial_state and custody_state are tracked and resolved independently. SETTLED + OUTSTANDING is a valid complete state for pays_for_cyl accounts. Neither state requires the other to be resolved first. 
}

Section 8

Cylinder Custody Model

  • CYL tracks both value balance (cyl_value_balance) and quantity balance (cyl_qty_balance_by_sku) per invoice.
  • Operational CYL CRNs (HDR_TOTAL = 0) reduce cyl_qty_balance_by_sku only. Applied deterministically on session load only when an exact SKU match to a prior-dated invoice exists. Ambiguous or unmatched operational CRNs route to the operational exception queue for operator manual assignment — never blindly auto-applied.
  • CYL pricing is static across all customers. Value = qty × static_price per SKU.
  • Customers with pays_for_cyl = true settle CYL liability by cash payment instead of physical return.
  • A dedicated CYL Custody Engine will handle full operational reconciliation post-MVP using erp_snapshots and movement_data.
MVP CYL Boundary
MVP is CYL-aware at sub-ledger level — it tracks value and qty balances per invoice. The future CYL engine handles yard counts, SOH snapshots, movement logs, and full custody chain reconciliation.
Section 9

Hard Domain Invariants

Hard Rule — Non-Negotiable
These are absolute engineering constraints. No exception handling, no operator override, no configuration flag changes them.
  • Payments may never settle future-dated invoices. invoice_date ≤ payment_date is enforced before scoring — future invoices are invisible to the scorer.
  • Zero-value CYL CRNs may never reduce monetary balances. They reduce custody qty only.
  • DEBIT_ADJUSTMENT always increases debtor exposure. It is never a settlement action.
  • ERP is read-only. No allocation, write-off, or classification is posted back to ERP in MVP.
  • Credit pool is never applied automatically. Operator must explicitly trigger credit pool usage.
  • All financial (monetary) allocations require operator confirmation. The engine suggests; it never acts autonomously on value balances. Deterministic operational CRN qty reconciliation (exact SKU match, prior-dated invoice) may auto-apply custody-only adjustments on session load — this does not constitute a financial allocation.

// Hard filter applied BEFORE scoring
const eligible = invoices.filter(inv => inv.date <= payment.date);
// Future-dated invoices are invisible to the scorer — no exceptions.

CRN Scoring

  • Closest prior date — primary signal (same constraint as PMT)
  • Amount proximity — ABS(CRN_remaining − invoice_component_balance)
  • Bucket similarity — fraction of CRN value in same bucket as invoice dominant bucket (≥70% defines dominant)
Note
Reference metadata (BANK_REF, CUSTOMER_REF) is low-trust for this customer base. Amount and date are the only reliable primary signals.

PMT Allocation Mechanics — Locked Rule

Hard Rule — PMT Targeting
A single PMT allocation action targets exactly: one PMT → one invoice → one sub-ledger component. No proportional split. No automatic spillover into other components. No silent distribution across the invoice.
StepWho decidesRule
1. Select target invoiceOperator (engine suggests via scoring stack)Must satisfy invoice_date ≤ payment_date. One invoice per action.
2. Select target componentOperatorFor single-component invoices: component is implicit. For mixed invoices (LPG + CYL + OTHER): operator must explicitly choose LPG, CYL_VALUE, or OTHER. Engine may suggest based on bucket dominance — never auto-select.
3. Apply amountEngineReduces selected component balance by MIN(pmt_amount, component_balance). If pmt_amount ≤ component_balance: component reduced, PMT fully consumed. If pmt_amount > component_balance: component reduced to zero, remainder routes to Suspense-PMT.
4. RemainderEngine routes, operator actsPMT remainder in Suspense-PMT is available for a subsequent allocation action. The engine may suggest the next best invoice + component, but must not perform the allocation automatically.

Worked example

// PMT R5,000 against a mixed invoice
PMT amount       : R5,000
Invoice LPG bal  : R3,000
Invoice CYL bal  : R2,000

Operator selects : LPG component

Result:
  LPG balance    : R3,000 → R0       (fully settled)
  CYL balance    : R2,000 → R2,000   (unchanged)
  PMT consumed   : R3,000
  PMT remainder  : R2,000 → Suspense-PMT

// CYL balance remains open. Engine suggests next action.
// Operator performs a second allocation to apply the R2,000 remainder.
// Engine never does this automatically.

What the engine must never do

  • Proportionally distribute a PMT across LPG, CYL, and OTHER components
  • Automatically spill a PMT remainder into the next component after one is settled
  • Auto-select a sub-ledger component for a mixed invoice
  • Chain allocation actions without an operator confirmation between each
Section 11

Item Awareness Rules

  • Item composition influences candidate ranking — it is never a hard constraint blocking allocation.
  • Cross-bucket allocation is always permitted but generates a warning.
  • Warning severity is controlled by the allows_cross_bucket_settlement customer flag.
  • Warning suppression is controlled only by the allows_cross_bucket_settlement flag. No automatic learning or historical rate inference.
FlagTypeEffect on Cross-Bucket Allocations
allows_cross_bucket_settlement = trueBOOLEANLower warning severity, minimal score penalty. Alert still shown.
allows_cross_bucket_settlement = falseBOOLEANHeavier score penalty, strong warning, explicit operator confirmation required.
pays_for_cyl = trueBOOLEANCYL cash settlement treated as normal. Alert tone softened accordingly.
mixed_invoices flag removed — mixed buckets are a document fact derived from detail lines, not customer configuration. The engine reads item composition directly from the invoice sub-ledger.

Section 17

Session Lifecycle

Session states: DRAFT → ACTIVE → COMPLETE → ARCHIVED. One debtor account per session, always.

Session Load Sequence

  1. Load all documents from ERP summary export for account + date range.
  2. Load DTRX payments from transaction_headers (Supabase) for account + date range.
  3. Load CYL qty data from transaction_items — build cyl_qty_balance_by_sku per invoice.
  4. Split CRNs: HDR_TOTAL ≠ 0 → financial queue; HDR_TOTAL = 0 → operational queue.
  5. Apply operational CRNs to cyl_qty_balance_by_sku deterministically — only when an exact SKU match exists on a prior-dated invoice. Any operational CRN without an unambiguous match routes to the operational exception queue for operator assignment. No blind auto-apply.
  6. Sign-split OBs: positive → INV lane (epoch anchor); negative → credit pool.
  7. Route all JNL and Bank UD to UNCLASSIFIED_EXCEPTION queue. Neither enters any financial lane until operator classification is complete.
  8. Seed all invoice sub-ledgers from detail lines (LPG / CYL / OTHER splits).
  9. Display session. Engine surfaces suggestions. Operator proceeds.

Session Output — Saved on Close

Audit Trail — MVP Scope
A formal queryable audit trail is deferred post-MVP. However, an append-only allocation log must be written for every session regardless — it costs near-zero and will be essential by month 3. The items below define the minimum required log content.
  • All allocation records (amounts, doc refs, operator ID, timestamp)
  • All exception lane assignments with reason codes
  • Credit pool movements (credit and debit events)
  • Reconstructed running balance at session close
  • Operator notes (if entered — never mandatory)
  • ROUNDING_WRITE_OFF records with approving operator ID
  • JNL / Bank UD classification decisions with classification type and operator ID
  • IGNORED document log (doc_id, operator_id, timestamp)
Section 18

Completion Rules

Hard Rule — Session Completion
Session is complete when: (1) every document has a terminal state AND (2) no UNCLASSIFIED_EXCEPTION remains AND (3) operator explicitly marks complete. ERP balance convergence is NOT a required condition.
Engine Warning — Balance Mismatch
When reconstructed balance ≠ ERP running balance: default assumption is ERP export is incomplete, not that allocations are wrong. Flag as informational warning only. Operator may override and complete with a noted discrepancy.

Section 19

UI Safety Contracts

  • DEBIT_ADJUSTMENT must use danger/red styling and show an explicit "Adds R[amount] to debtor balance" confirmation modal before saving. Must never resemble a settlement action.
  • Cross-bucket allocations must display a warning. Severity adapts to allows_cross_bucket_settlement flag.
  • UNCLASSIFIED documents must visually block allocation — operators cannot accidentally allocate an unclassified JNL.
  • Confirmation dialogs must show the affected sub-ledger component balances before and after the proposed allocation.
  • PMT against CYL component must trigger a separate alert: "Cash payment applied to CYL balance — verify physical return with operations."
  • Session completion button must be disabled until all documents reach a terminal state and no UNCLASSIFIED_EXCEPTION exists.
  • Credit pool application must be operator-initiated from a dedicated action — never presented as an auto-suggestion inline with regular allocation cards.

Section 23

Recommended Implementation Order

  1. Data schemas — invoice_sub_ledger, allocation_record, session, customer_config, exception_queue, classification_table, customer_credit_pool
  2. Session load pipeline — ERP parse → detail line seeding → DTRX fetch → operational CRN auto-apply → OB sign-split → JNL/Bank UD routing
  3. Scoring engine — composite scorer with hard past-only filter, date proximity primary, amount secondary, balance impact tertiary, FIFO tiebreak
  4. Allocation mechanics — sub-ledger reduction per operator-selected component, cross-bucket detection and alerts, PMT-to-CYL alert, PMT remainder routing to Suspense-PMT
  5. Exception lane UI — three financial lanes (Suspense-PMT, Suspense-CRN, Manual Hold-INV) + UNCLASSIFIED_EXCEPTION queue + OPERATIONAL_EXCEPTION queue (custody-only, does not block financial completion)
  6. JNL / Bank UD classification modal — enum picker with mandatory DEBIT_ADJUSTMENT danger styling
  7. Session completion validator — terminal state check + UNCLASSIFIED block + operator mark-complete
  8. Credit pool — persistent balance table, operator-triggered application, movement log

Section 25

Customer Configuration UX Rules

The spec defines two persistent customer flags: allows_cross_bucket_settlement and pays_for_cyl. This section defines exactly how and when those flags enter the operator workflow.

Hard Rule — Configuration Source
Customer configuration may only be created or changed by explicit operator action. The engine may never infer, self-update, or drift customer config based on historical allocation patterns. No counting logic. No threshold-triggered updates. Operator intent is the sole source of truth.

Core Design Principle — Friction-Born Configuration

Flags are not set through a settings screen that operators never visit. Configuration surfaces at the exact moment the operator experiences the relevant friction for the first time. This is the only UX contract that reliably produces correct configuration.

Anti-patternCorrect pattern
Operator navigates to Settings → Customer → FlagsFlag prompt appears inline at the first qualifying allocation event
System auto-sets flag after N overrides ("after 4 warnings")Prompt appears on the first occurrence — operator decides immediately
System infers flag from historical session dataOperator explicitly chooses "Always allow for this customer"

25.1 — allows_cross_bucket_settlement Flow

Triggered on the first cross-bucket allocation attempt in any session where the flag is not already set.

Trigger condition

// Flag prompt fires when ALL of the following are true:
operator attempts CRN or PMT allocation to a different bucket than the invoice component
AND customer_config.allows_cross_bucket_settlement IS NULL or false
AND this is the first cross-bucket attempt in this session

Warning modal — operator choices

ActionEffectPersists?
Proceed onceAllocation completes. Flag unchanged. Warning fires again next cross-bucket attempt.No
Always allow for this customerAllocation completes. allows_cross_bucket_settlement = true saved to customer_config. Future cross-bucket allocations show soft informational badge only — no blocking confirmation modal.Yes — customer level
CancelAllocation cancelled. No config change.No

Behaviour once flag = true

  • Cross-bucket allocations show a soft informational badge: "Cross-bucket commercial settlement"
  • No blocking confirmation modal
  • Score penalty for cross-bucket suggestions is reduced (engine still prefers same-bucket matches)
  • Flag is visible and editable from the session header customer info panel

25.2 — pays_for_cyl Flow

Triggered on the first attempt to apply a PMT to a CYL value sub-ledger component in any session where the flag is not already set.

Trigger condition

// Flag prompt fires when ALL of the following are true:
operator directs a PMT allocation to the cyl_value_balance component of an invoice
AND customer_config.pays_for_cyl IS NULL or false
AND this is the first PMT→CYL attempt in this session

Alert modal — operator choices

ActionEffectPersists?
Proceed oncePMT applied to CYL balance. custody_state remains OUTSTANDING. Alert fires again next PMT→CYL attempt.No
Mark customer as pays for cylindersPMT applied. pays_for_cyl = true saved. custody_state transitions to COMMERCIALIZED on operator confirmation. Future PMT→CYL alerts softened to informational.Yes — customer level
CancelAllocation cancelled. No config change.No

Behaviour once flag = true

  • PMT→CYL allocations show soft informational badge: "Cash CYL settlement — commercial account"
  • custody_state transitions to COMMERCIALIZED (not OUTSTANDING) when CYL value balance reaches zero
  • No blocking confirmation modal for subsequent PMT→CYL allocations
  • Flag visible and editable from session header customer info panel

25.3 — Customer Config Schema

customer_config {
  account_no                      TEXT      -- FK to customer account
  allows_cross_bucket_settlement  BOOLEAN   -- default: false
  pays_for_cyl                    BOOLEAN   -- default: false
  updated_by                      TEXT      -- operator ID who last changed config
  updated_at                      TIMESTAMP -- when last changed
}

25.4 — Config Editing Outside Workflow Prompts

Operators can also view and change flags from the session header customer info panel at any time — not just at the friction moment. This handles cases where a flag was set incorrectly or a customer's commercial behaviour changes.

  • Config changes from the session header take effect immediately for the current session
  • All config changes are logged: account_no, flag changed, old value, new value, operator_id, timestamp
  • Config log is append-only — no silent overwrites
Note — Why Not "After N Warnings"?
Prompting after N repeated overrides is still inference-driven UX — the system is counting behaviour and deciding when to surface config. The correct model is first-occurrence prompting: the operator sees the decision on the first qualifying event and makes an explicit choice. No counting. No hidden thresholds.
