## 1. The correction — Nov 2025–Dec 2025 occurrences were coincidence

I traced every payment batch (`STAT 120`–`STAT 125`) line by line, checking
each payment's amount against the *full* amount of the invoice its `INVNO`
references:

```
STAT 120 (18/11, 26/11/2025): 47420, 47662, 47666, 47838, 47887 — every
  line pays its invoice's FULL amount exactly (47666 off by R0.36, an
  isolated rounding gap, immaterial).
STAT 121 (08/12, 13/12/2025): 47941, 48130, 48185 — same, all EXACT.
STAT 123 (02/02, 18/02/2026): 48975, 48979, 49100, 49228, 49259 — same,
  all EXACT.
```

**Every invoice in these three batches is cleanly, fully, individually
matched — nothing partial, nothing blank.** The account's running balance
landing on exactly `-R454.09` after each of these batches is **pure
arithmetic coincidence** of that batch's specific invoice amounts — not
evidence of a tracked, carried-forward float. There is no single R454.09
item that has existed since November 2025. That claim is retracted.

## 2. Where a real, traceable mechanism *does* start: March 2026

Tracing `STAT 122` (20/01/2026) and `STAT 124` (06/03/2026) the same way
surfaced something different — a genuine partial-payment pattern, and it's
not unique to this account or this period:

**Invoice `00049360`** (R1,184.37, raised 21/02/2026) was settled via
**two separate, individually-tagged (not blank) payment lines**, three
weeks apart:

| Date | Batch | Amount | Running total |
| :--- | :--- | ---: | ---: |
| 20/01/2026 | STAT 122 | -R454.09 | |
| 06/03/2026 | STAT 124 | -R730.28 | |
| | | **-R1,184.37** | matches invoice exactly ✅ |

(Yes — the first fragment is dated *before* the invoice it settles even
existed. That's a real feature of this ERP export, not an error: a payment
*line's* date is when the transfer was originally posted; `INVNO` tagging
can be applied retrospectively once a later invoice is raised and the
bookkeeper allocates the earlier float against it. Confirmed this is not a
one-off — **10 different invoices** across TAN002's 3-year history were
each settled via 2 or more separately-dated payment fragments, e.g. `42427`
(6 fragments), `48351` (3), `39479`/`40709`/`37245`/`41584`/`47666`/`48353`
(2 each). Multi-fragment settlement is a normal, recurring feature of how
this account gets paid — invoice 49360 is not exceptional.)

**Separately, in the very same STAT 124 batch, one line has no `INVNO` at
all:**

| Date | Batch | Line | Amount | INVNO |
| :--- | :--- | :--- | ---: | :--- |
| 06/03/2026 | STAT 124 (doc 00043562) | 1st of 4 | -R454.09 | **blank** |

This is coincidentally the exact same figure as invoice 49360's first
fragment, but it's a different transaction (different position in a
different batch) and the ERP genuinely never recorded what it was for.

**And on 21/04/2026, a single-line payment (STAT 125) also carries no
`INVNO`:**

| Date | Batch | Amount | INVNO |
| :--- | :--- | ---: | :--- |
| 21/04/2026 | STAT 125 (doc 00044064) | -R1,193.96 | **blank** |

This one exactly equals the shared amount of two invoices raised days
apart, 28/03 (`00049971`) and 31/03 (`00050035`) — both R1,193.96, both
otherwise completely unmatched by anything. Every other multi-line batch in
this account's entire 48-batch history closes invoices in strict ascending
doc-number/date order with zero exceptions found; applying that pattern
here would point to `00049971` closing and `00050035` staying open. **Per
the correction above, this is now downgraded further than "ASSERTED": it's
a guess about which invoice an algorithmic allocation process picked, not
about which invoice the debtor's payment actually related to.** The TXT
doesn't say which, DB access (obtained later this session) didn't resolve
it either — `ref_no` on this payment line is blank in `transaction_headers`
too (see `TAN002_DB_CN_Tax_Convention_Bug_2026-09-22.md` §5) — and even if
it weren't blank, per this correction the value wouldn't settle the
question of debtor intent anyway. Only the STAT 125 remittance advice or
bank record can actually answer this.

## 3. So what is R739.87, precisely?

Not one document. It's an emergent figure:

```
  R1,193.96   open invoice (00049971 or 00050035 — WHICH one is an
              unverified guess, see correction above, not a fact)
−  R454.09   unattributed payment received 06/03/2026 (blank INVNO, never
              matched to any document, anywhere in this account's history)
────────────
  R739.87
```

The R454.09 didn't "sit there waiting" for 8 months — it reduced the
account's cash-owed position the moment it was received (6 March 2026) and
that reduction carries forward in the running balance permanently, same as
any payment. It just never got tied to a specific invoice in the ERP's own
export. Net effect on today's exposure: real, but it's a **credit in the
debtor's favour that's never been formally allocated**, not a debt.

## 4. What R454.09 actually is — not resolved, but narrowed

Checked whether R454.09 (or R739.87) is itself a recognisable recurring
charge: **no invoice or credit note anywhere in TAN002's 3-year history was
ever raised for exactly R454.09 or R739.87.** Rules out "a specific fixed
fee/line-item that's perpetually short-paid."

Given multi-fragment invoice settlement is normal for this account (§2),
the most defensible reading is that this is simply another payment
fragment of that same kind — just one the ERP's own allocation process
never finished tagging — rather than anything exotic. A bank/EFT fee
skimmed from a larger transfer is possible but R454.09 is large for that
(typically far smaller); not ruled out, just not favoured.

**This cannot be resolved further from the TXT.** It needs either:
- DB-level allocation detail (`vw_clean_transactions` / `transaction_headers`
  for doc `00043562`), or
- the actual STAT 124 remittance advice / bank statement for 06/03/2026.

## 5b. The account's TRUE last full clear-to-zero: 17/02/2025, not 21/10/2024

Found this working chronologically backward from R739.87, in conversation
with the operator, using **pure balance arithmetic — no `INVNO` involved**:

**The account was exactly R0.00 nineteen times between 19/09/2023 and
21/10/2024**, then — reading the export's own row order — never again.
But that reading is distorted by a file-boundary artifact: payment
`00036865` is filed as the *first* row of `raw/TAN002CURRENT.TXT`
(ERP-posted date 22/02/2025, applied against the R16,828.85 B/F carried
from `raw/TAN002_2025.TXT`'s 27/02/2025 close) — even though, per
operator-supplied context, its true value date was **17/02/2025**.

Reconstructing the ledger with that true date:
- Balance per `raw/TAN002_2025.TXT`'s own running total, as of the last
  transaction on/before 17/02/2025 (CN `00011909`/invoice `00040766`,
  both 17/02): **R12,282.56**.
- Payment `00036865`'s total (all 9 lines): **-R12,282.56**.
- Sum: **R0.00**, exact to the cent.

That's a **20th** exact-zero point, later than 21/10/2024 by nearly four
months, hidden by the export's date ordering rather than absent. The
account's true persistent-carry era is **~18 months (17/02/2025 → today)**,
not the ~22 months first implied by the raw export order.

**The very next payment cycle already fails to fully clear.** Reconstructing
forward from the 17/02/2025 zero (merging `TAN002_2025.TXT`'s remaining
Feb rows with `TAN002CURRENT.TXT` in true chronological order) reproduces
the known 27/02/2025 closing balance exactly (R4,546.29 either way — pure
arithmetic identity, order doesn't change a sum). From there:

| | Balance |
| :--- | ---: |
| Balance immediately before payment `00037780` (27/03/2025) | R11,770.14 |
| Payment `00037780` total | -R10,431.35 |
| **Balance after** | **R1,338.79** |

Confirmed: the balance never returns to exactly R0.00 again anywhere in
the rest of the export, from this point through today. **R1,338.79 was
unpaid from that batch payment** — payment `00037780` closed 6 tagged
lines but left this amount off the account's running balance.

Notable, and worth recording even though it isn't proof of a specific
cause: **R1,338.79 is one cent off invoice `00041270`'s own face amount
(R1,338.78)** — an invoice that was itself paid *in full*, within this
same batch, on the same date. Circumstantial (this ledger has many
similarly-sized invoices; per the `INVNO` correction above, no tag claims
this residual belongs to `41270`), but the arithmetic proximity plus the
fact that it sits in the very same batch is close enough to be worth
flagging as a candidate explanation for how this specific batch came up
one invoice-unit short, rather than dismissing it as pure noise.

This refines, rather than contradicts, §1's correction: the account's
permanent-carry era starts in **2025** (17/02/2025 → 27/03/2025 is the
actual transition), not November 2025 as first (wrongly) claimed, and not
21/10/2024 either — the true starting point was hidden by an export
artifact the whole time.
